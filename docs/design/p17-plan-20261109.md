# P17 — 32-bit (x86) applications (M9)

Windows runs 32-bit programs (WOW64) on real 32-bit builds of the Win32
DLLs; only the system call boundary changes processor mode. Doors follows
that shape:

- The compatibility DLLs are built a second time for `i686-pc-windows-msvc`
  (stdcall exports). Window procedures, COM vtables, thread starts, TLS
  callbacks and SEH handlers stay 32-bit end to end: no reverse thunks.
- The one boundary is `door_sys::raw`: on i686 every Door system call widens
  its arguments into a block of 64-bit words, far-calls the 64-bit user code
  segment (0x33), executes `syscall` there and far-returns to the 32-bit
  segment (`runtime/sys`, `door_gate64`; encoding checked with dumpbin:
  `9A … 33 00`, REX-prefixed 64-bit body, `CB`). Kernel ABI structures use
  fixed-width fields, so a pointer below 4 GB means the same on both sides.
- Windows-facing exports take pointer-width parameters (`usize`) and widen
  each one explicitly at entry (`door_windows_abi::widen`: sign extension,
  correct because every address of a 32-bit Doors process lies below 2 GB,
  and it keeps -1/-2 pseudo-handles and INVALID_HANDLE_VALUE); pointer and
  handle results are narrowed. Door-private exports between Doors' own DLLs
  keep 64-bit parameters (both sides are the same build).

## Kernel

- GDT entry 7: 32-bit user code (L=0, D=1, DPL 3), selector 0x3B
  (`USER_CODE32_SELECTOR`); 0x2B data and 0x33 64-bit code are shared.
- IRET validation accepts 0x3B only with instruction and stack pointers
  below 4 GB.
- CSTAR (SYSCALL from compatibility mode, AMD only; Intel raises #UD) enters
  `door_syscall_compat_entry`, which reports an invalid-opcode fault of the
  32-bit program: never a way into the kernel.
- Address space: the existing user layout (heap 0x5000_0000, thread stacks
  and pages 0x6000_0000, the main stack 0x7000_1000, the startup block and
  TEB/PEB 0x7100_xxxx, sections 0x7200_0000..0x8000_0000) already lies below
  2 GB; an x86 process places its images there too: the executable at its
  32-bit base and the 32-bit DLL slots from 0x0200_0000.
- A 32-bit thread's FS base is its TEB32 (`door_windows_abi::x86`): the SEH
  chain at 0, stack bounds, self at 0x18, ids at 0x20/0x24, the implicit TLS
  array at 0x2C, the PEB32 at 0x30, the last error at 0x34, Doors' dynamic
  TLS slots at 0x400 (the GDI batch area no program addresses).

## Loader (compat/pe, door-image-format)

- `PeImage::parse_any` reads PE32 (machine 0x14C, optional header 0x10B: a
  4-byte image base, data directories at offset 96). The x64 entry points
  keep refusing PE32.
- `LoadPolicy::Application32`: every module x86 and wholly below 4 GB;
  HIGHLOW relocations, 4-byte import thunks (IMAGE_ORDINAL_FLAG32), the
  32-bit TLS directory (24 bytes), IMAGE_LOAD_CONFIG_DIRECTORY32 read into
  the 64-bit field offsets, its SafeSEH table validated (sorted handler
  RVAs inside the image) and kept for the x86 dispatcher, the x86 /GS
  default cookie (0xBB40E64E) rewritten with a 32-bit diversified value,
  `IMAGE_FILE_32BIT_MACHINE` required, no exception directory, no
  position-independent placement without relocations. `Fixup.width` tells
  the kernel how many bytes to write.
- Real MSVC x86 fixtures: `compat/pe/tests/data/x86` (`build.md`).

## Progress (11 November 2026): x86 processes, the 21 DLLs, WOW64 views

### Processes and exceptions

- The kernel plans an x86 process with `Application32` over the 32-bit DLL
  catalog (`door_windows_abi::modules::PROVIDERS32`, 16 MiB slots from
  0x0200_0000), builds its PEB32/TEB32 and static TLS vectors, enters CS
  0x3B with the bootstrap in ECX, and starts 32-bit threads the same way.
  DS, ES and FS hold the user data selector 0x2B (a null selector faults in
  compatibility mode on hardware virtualization). Relocations may cross a
  page inside one section, as Windows allows.
- `PROCESS_MACHINE` (0x308) answers 0x14C or 0x8664 for a process handle;
  telemetry marks x86 processes (`MODE_X86`) and Task Manager names them
  "… (32 bit)", as Windows 11 does.
- A fault in 32-bit code reaches 32-bit ntdll as an EXCEPTION_RECORD32 and
  CONTEXT32 (`deliver32`); `seh32.rs` runs the vectored handlers, then the
  SEH chain from `fs:[0]` (frames checked against the TEB32 stack bounds),
  continues by loading the CONTEXT32, and implements RtlRaiseException and
  RtlUnwind; kernel32 exports RaiseException and RtlUnwind for x86.

### Structures at the program's width

`door_windows_abi::layout` describes a Windows structure once as its field
kinds (U8/U16/U32/U64/Pointer/Bytes) and lays it out as MSVC does for the
build's width: natural alignment, 8-byte integers aligned to 8 on x86 too,
`#pragma pack` (shellapi.h's pack 1 on x86, mmsystem.h's pack 1). Every DLL
reads and writes program memory through it or through pointer-width
`read_pointer`/`write_pointer` helpers: OVERLAPPED(_ENTRY), STARTUPINFO,
PROCESS_INFORMATION, IO_STATUS_BLOCK, handle arrays, WNDCLASSEXW, MSG,
CREATESTRUCT, WINDOWPOS, the comctl32/comdlg32 structures, security
descriptors and SCM records, SHFILEOPSTRUCT and NOTIFYICONDATA, WSADATA,
fd_set, WSAPOLLFD, WSABUF, addrinfo, hostent/servent/protoent,
IP_ADAPTER_ADDRESSES/INFO and FIXED_INFO, ICMP_ECHO_REPLY, DNS_RECORD and
DNS_QUERY_REQUEST/RESULT, URL_COMPONENTS and the WinHTTP/WinINet proxy and
async records, INTERNET_CACHE_ENTRY_INFO, WAVEHDR, MIDIHDR, the MCI
parameter blocks and mixer records, DSBUFFERDESC and DSBPOSITIONNOTIFY,
PROPVARIANT, MULTI_QI, STATSTG, RPCOLEMESSAGE, VARIANT, SAFEARRAY,
DISPPARAMS, EXCEPINFO, TYPEATTR, FUNCDESC, VARDESC, ELEMDESC, CUSTDATA,
INTERFACEDATA. COM vtables are read as tables of pointer-sized entries; a
VARIANT parameter passed by value (Task Scheduler's) is a by-value struct,
which the x64 ABI passes by address and the x86 one on the stack.

### The 21 DLLs

Every compatibility DLL (`NAMES32` = `NAMES`) builds for
`i686-pc-windows-msvc` and links against the others' 32-bit import
libraries. Exported callbacks and function-pointer types are pointer width;
ntdll's Windows-facing exports (heap, vectored handlers, NtWriteFile,
NtQuerySystemTime, …) take `usize`, its `Door*` private exports keep 64-bit
parameters. oleaut32's IDispatch::Invoke and DispCallFunc call through an
x86 thunk (arguments pushed by type, 8-byte values as two words, a
VARIANT/DECIMAL by value as 16 bytes, floating-point results from ST0).

### Redirection and views (WOW64)

- Files: a 32-bit process's `C:\Windows\System32` resolves to
  `C:\Windows\SysWOW64` (except catroot, catroot2, driverstore,
  drivers\etc, logfiles, spool), `Sysnative` to the real System32;
  Wow64DisableWow64FsRedirection/Revert and
  RtlWow64EnableFsRedirectionEx switch it per thread (TEB32 0x3F8); the
  x64 entry points fail with ERROR_INVALID_FUNCTION as on Windows.
- Registry: the 32-bit view of HKLM\SOFTWARE is WOW6432Node, with Windows'
  shared-key list and the Classes redirection (CLSID, Interface, …);
  KEY_WOW64_64KEY/32KEY choose a view. The CurrentVersion folder values of
  both views are seeded as Windows 11 holds them, and App Paths exists.
- Environment: a 32-bit process sees PROCESSOR_ARCHITECTURE=x86,
  PROCESSOR_ARCHITEW6432=AMD64 and the (x86) Program Files variables; an
  x64 child of it gets the 64-bit values back.
- Known folders: ProgramFiles and ProgramFilesCommon are the (x86) ones for
  a 32-bit caller, ProgramFilesX64/CommonX64 are not found (0x80070002),
  SystemX86 is SysWOW64; Common Files exists in both trees.
- IsWow64Process and IsWow64Process2 report a 32-bit process as WOW64 on
  AMD64 and an x64 one as not.

### Fixtures (MSVC x86, Windows SDK, no C runtime)

- X86-A `x86probe.exe` (8 steps) and X86-B `x86gui.exe` (10 steps, user32
  and gdi32 structures each followed by a canary): `cargo xtask test
  p17-x86`.
- X86-C `wowprobe.exe` (5 steps: environment, folders, registry,
  redirection, an x64 child `wowchild.exe`), then from an elevated Terminal
  `wowprobe.exe guest`: a 32-bit installer's HKLM, System32 and Program
  Files writes, verified and removed by the x64 child through the 64-bit
  views: `cargo xtask test p17-wow64`.
- The expected outputs come from the same binaries run `raw` on the
  owner's Windows 11 26H2 (read-only; `guest` mode never runs on a real
  PC).

### Limitations

- SafeSEH tables are kept but not enforced; no SEHOP, nested-exception
  frames or collided unwinds.
- Reloading FS from user mode loses the TEB32 base (the descriptor is the
  shared data selector).
- PEB32 ProcessParameters32 (the 32-bit layout) carry only the image path,
  command line and environment.
- SysWOW64 holds no DLL files: the 32-bit DLLs load from the initfs
  catalog, so a program that opens one as a file does not find it.
- Enumerating the 32-bit registry view omits the shared keys.
- oleaut32's universal marshaler (type-library proxies and stubs,
  PSOAInterface/PSDispatch) is x64-only: a 32-bit process's
  DllGetClassObject answers CLASS_E_CLASSNOTAVAILABLE for it, so
  CoMarshalInterface fails there for type-library interfaces.

## Critic close-out (11 November 2026)

The read-only P17 critic (`reports/critics/p15-p17-critic-findings-20261111.md`)
did not accept the phase as first reported; every finding was fixed, then a
second read of the fixes raised the loader items below, also fixed.

- **Selectors**: every return to user mode reloads DS, ES and FS with 0x2B
  (a null or 0x3B selector no longer reaches the next thread); SYSENTER's
  MSRs are cleared; CONTEXT32 reports SegFs 0x53 as Windows does (ADR 0023
  records that `mov ax, fs` reads 0x2B).
- **Programs and DLLs**: a 32-bit msvcrt.dll (errno in the TEB32);
  SysWOW64\msiexec.exe, a real i686 build (`msiexec-x86`), so a 32-bit
  package installs in the 32-bit engine and CreateProcess("msiexec ...")
  works from a 32-bit process; PE characteristics accepted as Windows
  accepts them; a full-page TEB32 with DeallocationStack and the TlsSlots
  mirror at 0xE10; PEB32 ProcessParameters32; the 2 GB limit and placement
  of large executables; fault translation (#BP, #GP, #MF, #XM).
- **LoadLibrary** (second pass): Doors' system DLLs from the catalog, then
  Windows' safe search order (`door_windows_abi::dll_search`): a KnownDLL
  only from System32; otherwise the application's folder (a native image
  path such as `/system/bin/x86probe.exe` included), System32, the Windows
  folder, then the current directory, which is never searched for a name
  Windows ships in System32 (3,758 names hashed from Windows 11 26H2);
  LOAD_LIBRARY_SEARCH_* restrict the folders; ".dll" is appended to a bare
  stem. LoadLibraryEx's data-file flags answer a loaded module or a Doors
  system DLL with the module, otherwise lay the file (at most 64 MiB; the
  PE header offset checked) out for the resource functions.
  DONT_RESOLVE_DLL_REFERENCES loads normally.
- **Fixtures**: X86-A step 10 reads x86dll.rc's RCDATA through a
  LOAD_LIBRARY_AS_DATAFILE handle (`resource=1`); the probe passes 10/10 on
  Windows 11 26H2 (`compat/dlls/kernel32/tests/reference/x86probe-raw.txt`).
  X86-A's unwind and relocated-DLL steps (DllMain, TLS) were added after the
  first critic pass.
- **Gate**: `Phase::P17` inherits P16's gate and adds the i686 lints of the
  21 DLLs and msvcrt.dll, the door-windows-abi and door-pe-loader suites,
  p17-x86 and p17-wow64.
