# P18 managed and modern application frameworks — proposed plan

Status: proposal, 11 November 2026. Nothing here is implemented; the phase
ledger keeps P18 `not_started` until the owner accepts the plan and its
decisions (the questions at the end).

## What the specification asks

The master specification's roadmap row for P18 (section 91): runtime,
GC and JIT support, .NET profiles, Windows Forms and WPF, the WinRT,
WinUI and package tracks, and browser, Electron and WebView
dependencies, after P10, P13, P15 and P16. Exit: each exact runtime or
framework completes a named workflow; no blanket family claim from a
console hello-world. Work packages RUNTIME-A (JIT/GC/runtime hosting,
managed APIs, WinForms/WPF, WinRT/package/App SDK dependency packets) and
BROWSER-A (process sandbox, shared memory, network, certificates, text,
media, GPU, browser runtime and deployment). Sections 69, 70, 108 and 110
add the rules this plan follows:

- Each runtime is either an unmodified Windows distribution run through
  the compatibility layer or a native Door port; record which, with the
  binary identity, in every scenario. This plan uses unmodified Windows
  distributions throughout: that is what Windows applications ship and
  what a native port could not prove.
- Prefer approved upstream runtimes to rewriting them; pin versions, keep
  their licenses, never accept proprietary redistributable terms without
  the owner.
- Unlock reusable bottlenecks first (asynchronous I/O, loader, TLS and
  exceptions, COM apartments, windowing, text metrics, graphics
  correctness, installer lifecycle); application-specific shims are
  exceptions with a removal condition.
- A workflow is sustained and useful (allocation, threads, I/O,
  exceptions, shutdown; multi-window forms, dialogs, DPI change and
  persistence; navigation, downloads, permissions and subprocess
  failure), with its failure handling.

## Where Doors stands (measured 11 November 2026)

What P10 to P17 already give a runtime: PE32 and PE32+ loading with
private DLLs (four per process) and data-file loads, TLS and SEH on both
widths, threads, waits, I/O completion ports, overlapped Winsock,
WinHTTP and WinINet over Doors' TLS 1.2 client, crypt32 and wintrust,
COM apartments, out-of-process activation and Automation, the SCM,
Windows Installer with WOW64 views, and a scoped original msvcrt.dll.

The blockers each runtime meets first, found by reading their import
tables and runtime contracts against Doors:

1. **The registry store**: 128 keys and 384 value records per volume,
   48-unit names, 2 KiB values, the hive rewritten whole per change. The
   .NET installers and runtime registration alone exceed it.
2. **No executable dynamic memory**: VirtualAlloc'd memory is never
   executable (P03/P05 W^X). CoreCLR's JIT (with W^X mode, the default
   since .NET 7, it maps code twice: RW and RX views of one section),
   V8 and HotSpot all need it.
3. **No Universal CRT**: CoreCLR, the .NET host, Python, OpenJDK, Node
   and Electron import `api-ms-win-crt-*` (ucrtbase.dll); .NET uses the
   hybrid CRT (static VCRuntime, dynamic UCRT).
4. **Unwinding JIT code and suspending threads**: dynamic function tables
   (RtlAddFunctionTable, RtlInstallFunctionTableCallback), Get/
   SetThreadContext on suspended threads, FlushProcessWriteBuffers,
   QueueUserAPC, vectored handlers (the GC's thread suspension and
   hijacking).
5. **Address space**: the .NET GC (regions) reserves 256 GB up front;
   reservations must be cheap and unbounded by commit.
6. **Globalization**: without icu.dll, .NET uses the NLS functions
   (CompareStringEx, LCMapStringEx, FindNLSStringEx, GetLocaleInfoEx,
   calendars, time zones), which Doors covers only partly.
7. **SSPI/Schannel**: .NET's SslStream and HttpClient use secur32's
   Schannel package, not WinHTTP.
8. **Side-by-side activation contexts**: comctl32 v6 for Windows Forms
   (application manifests, CreateActCtx).
9. **GDI+** (gdiplus.dll) for Windows Forms' drawing; **DirectWrite**
   for WPF text and Chromium; Direct3D 9 for WPF's hardware path (its
   software path suffices).
10. **Capacity**: 13 processes, 8 kernel ports, four private DLLs per
    process, and executables of at most 1 MiB (`EXECUTABLE_MAX_BYTES`:
    Init captures a program whole before it maps it); `dotnet.exe`,
    `java.exe` and `node.exe` are larger, a browser runs five or more
    processes, and .NET loads many managed and native modules.
11. **Services and sessions**: no non-interactive desktop; sandboxing
    needs job objects, restricted tokens and integrity levels.
12. **CNG**: .NET's System.Security.Cryptography, its random numbers and
    certificate handling call bcrypt.dll and ncrypt.dll (algorithms,
    BCryptGenRandom, persisted keys); Doors has CryptoAPI (advapi32) and
    crypt32 but no CNG.
13. **The VC++ runtime**: applications and runtimes ship vcruntime140.dll
    and msvcp140.dll beside themselves (Microsoft's app-local
    redistribution); C++ exceptions go through `__CxxFrameHandler4` and
    RtlUnwindEx, and those DLLs import the UCRT's API sets. Today's 32-bit
    msvcrt.dll has only a stub frame handler.
14. **Named pipes and shared sections at scale**: .NET's diagnostics,
    Python's multiprocessing, Node's IPC and every browser's broker use
    named pipes and file mappings between processes; Doors has anonymous
    pipes only, and no CreateFileMapping or job objects.
15. **The volume itself** (found 12 November 2026 reading `storage/ext2.rs`
    and `persistence/namespace.rs`): the persistent C: drive is one ext2
    block group, 8,192 blocks (32 MiB) and 128 inodes; files stop at
    4,243,456 bytes (direct and single-indirect blocks only); the
    namespace holds 256 files and folders in a 68 KiB catalog rewritten
    whole by every change, with 48-unit names, and 16 opens. One .NET
    runtime is about 70 MB in roughly 200 files, several over 4 MiB and
    some names over 48 units (`Microsoft.Extensions.DependencyInjection.Abstractions.dll`).
    The registry limits of item 1 are the same design. Storage comes first.

## Milestones

Each milestone ends with its guest evidence, records, and one read-only
critic, as P15 to P17 did. Fixtures first (independently built with the
pinned MSVC toolchain), then the named application.

### M0 — platform prerequisites (bottlenecks shared by every track)

- **M0a Storage v2: the volume, the namespace and the registry at scale.**
  One design for blocker 15 and blocker 1, in five steps, each with its
  host tests, crash tests at every journal checkpoint and a guest run:
  1. *ext2 at scale.* The same standard ext2 revision 1, now with any
     number of 32,768-block groups (per-group descriptors, bitmaps and
     inode tables, `sparse_super` superblock copies written at format),
     inodes sized at format, double- and triple-indirect blocks and
     `large_file` sizes. Backing objects live in 256 hashed folders
     (`oXX/obj<id>`) so no directory grows past a few blocks, and the
     catalog opens them by inode and generation, not by name. Mount
     checks the superblock, descriptors and bitmap counts; the full
     cross-check of every inode and block becomes an offline audit
     (`xtask storage audit`) instead of an O(volume) step at every boot.
     The old one-group volumes stay mountable (they are a valid subset),
     so every P06/P07 profile and its evidence is unchanged.
  2. *A paged B+tree* (`storage-core`, allocation-free): 4 KiB pages in
     one file, a caller-provided static page cache, variable-length keys
     and records, case-folded name comparison, updates written in place
     through the existing redo journal (a change writes only the pages
     it touches, at most a handful). Anything larger than one
     transaction (a 1 MiB value, a file truncated by gigabytes, a deleted
     key with thousands of values) is written to pages listed in the
     header's intent record first and linked by one final transaction;
     mount finishes or frees whatever an interrupted intent lists, so no
     scan of the whole tree is ever needed.
  3. *Catalog v6 on the tree.* Nodes by id and by (parent, folded
     name); file names to 255 UTF-16 units; ACLs, attributes, times and
     backing identity per node; nodes, opens and handles bounded by the
     volume and the service's memory, not by fixed arrays.
  4. *Registry hive v2 on the same tree.* Keys by id and by (parent,
     folded name), values by (key, insertion order) with a lookup index
     by (key, folded name): key names to 255 units, value names to
     16,383, values to 1 MiB, subkey enumeration sorted as Windows
     returns it, open handles to deleted keys kept as today, versions and
     change notifications unchanged.
  5. *Migration and tools.* The first mount of a catalog v1 to v5 volume
     (with its hive v1) converts it losslessly in bounded transactions
     behind an intent record, and the independent audits in `xtask`
     learn the new format. Disk profiles gain a large home volume (sparse
     image files on the host), the old profiles stay byte-identical.
  Then the Compatibility tab (AppCompatFlags\Layers with full-path value
  names: version lie, Run as administrator, DPI) that waited on long names.
- **M0b design (13 November 2026, measured on the kernel).** Today a
  Windows process's dynamic memory is whole regions: one reservation of at
  most 65,536 pages, committed all at once into physically contiguous
  frames with a kernel alias, 160 regions per process, 256 MiB of dynamic
  address space, RO or RW only, and VirtualProtect only on a whole
  reservation. CoreCLR reserves gigabytes (the regions GC reserves
  256 GiB), commits and protects page ranges inside them, and maps
  executable views; V8 does the same for its code space. So M0b is a VM
  change before it is a permission change:
  1. *Sparse reservations.* The Windows personality gets the user half
     above the image and DLL window (128 TiB), reservations tracked in an
     ordered table of (start, pages) with no fixed page cap; reserving
     costs no frames and no page-table pages.
  2. *Page-granular commit.* Committed pages are recorded in the process's
     own page tables plus a per-reservation bitmap (commit charge counts
     pages, against the manifest's budget). The frame allocator keeps 640
     allocation records and the kernel has no direct physical map, so
     pages come from a kernel page pool: 4 MiB chunks, each one frame
     allocation and one kernel alias, sub-allocated by a per-chunk bitmap
     and zeroed through the chunk's alias; a chunk whose pages are all
     free goes back to the frame allocator. MEM_COMMIT, MEM_DECOMMIT and
     MEM_RESET on any page range; VirtualQuery returns Windows' region
     runs (same state and protection). Each process's page-table pool
     (256 table pages, 512 MiB of dense 4 KiB mappings) grows on demand.
  3. *Protections per page:* NOACCESS, READONLY, READWRITE, EXECUTE,
     EXECUTE_READ, plus GUARD (a one-shot fault Windows raises as
     STATUS_GUARD_PAGE_VIOLATION, which thread stacks and CoreCLR use).
     W^X per page (owner): EXECUTE_READWRITE and EXECUTE_WRITECOPY are
     accepted and kept W^X by fault toggling: the page starts RW; an
     instruction fetch faults, the kernel flushes it to RX on every CPU
     and resumes; a later write faults back to RW. A page is never
     writable and executable at once, and callers that ask for RWX still
     work (at a fault per switch). Per-process policy (on by default, as
     Windows) via SetProcessMitigationPolicy(ProhibitDynamicCode).
  4. *Executable views of sections* for CoreCLR's double mapping:
     MapViewOfFile(FILE_MAP_EXECUTE) maps a pagefile-backed section RX in
     one view and RW in another; physical W^X stays per view pair (the RX
     view is never writable, the RW view never executable).
  5. *FlushInstructionCache* (a serializing no-op per CPU on x86 after the
     TLB shootdown the protection change already did) and
     FlushProcessWriteBuffers (an IPI to every CPU running the process).
  Work list (drafted 13 November 2026 while the P17 gate ran; files not
  yet wired into the build): `kernel/src/mm/page_pool.rs` (4 MiB chunks,
  per-chunk bitmap, zero on reuse, empty chunks returned) and
  `kernel/src/mm/user_table/pages.rs` (per-page leaves with the Windows
  protection in software bits, guard pages, the W^X toggle on fault, empty
  table reclamation), both with host tests. Still to do: the per-process
  reservation table and sparse arena (fixed-address VirtualAlloc checks
  both it and the image/section regions), VM_COMMIT/DECOMMIT/PROTECT on
  page ranges, a new VM_QUERY operation and kernel32's VirtualQuery(Ex)
  (absent today; CoreCLR and V8 call it constantly), the fault hook
  (toggle, guard -> STATUS_GUARD_PAGE_VIOLATION, else access violation),
  executable section views, FlushInstructionCache and
  FlushProcessWriteBuffers, SetProcessMitigationPolicy, and guest
  fixtures (a JIT-style RW->RX stub, a guard-page stack probe, RWX
  toggling, VirtualQuery runs).
  The VM model itself (measured 13 November 2026): every user region is
  physically contiguous and keeps a permanent kernel alias inside the
  process's 64 MiB kernel window (`PROCESS_STRIDE`; the first 1 MiB is the
  page-table pool of 256 pages, the rest image aliases), the frame
  allocator has 640 allocation records machine-wide, and images are
  captured whole (1 MiB executable limit). libcef.dll alone is about
  200 MB and VS Code's Electron executable about 150 MB, so M0b and M0h
  share one VM change, done first:
  1. *No standing kernel aliases for user memory.* User pages come from the
     page pool (`kernel/src/mm/page_pool.rs`, drafted) one at a time; the
     kernel reaches a user page through the user copy path or a short-lived
     per-CPU mapping window, never a permanent alias.
  2. *Growable page-table pools.* `UserTable` takes table pages from the
     page pool and finds them by physical address in a small per-process
     index, not by offset into one contiguous 1 MiB block.
  3. *Images mapped from the file.* PE sections are read page by page into
     pool pages (shared read-only pages of the same file between processes
     later), so the image size limit becomes the address space, and the
     process window no longer holds image aliases.
  4. *Sparse Windows reservations* (`kernel/src/mm/reservations.rs`,
     drafted with tests): sorted per-process table, 1,024 entries, no page
     cap, checked against regions both ways.
  Kernel limits sized from the targets (owner: raise as needed): regions
  become reservations with no table cap beyond the commit budget; the
  dynamic commit budget of a Windows process goes from 256 MiB to the
  machine's RAM share set by its manifest (2 GiB on the desktop profile).
- **M0b Dynamic code.** Executable dynamic memory with W^X kept per page:
  VirtualProtect transitions RW to RX and back, MapViewOfFile with
  FILE_MAP_EXECUTE (CoreCLR's double mapping), FlushInstructionCache, and
  a per-process dynamic-code policy (on by default as on Windows;
  SetProcessMitigationPolicy can turn it off). Needs the owner's approval:
  it changes the P03/P05 rule that no user memory becomes executable after
  load.
- **M0c Runtime support in ntdll/kernel32.** Dynamic function tables and
  their callbacks in RtlVirtualUnwind and the exception dispatcher;
  Get/SetThreadContext on suspended threads; FlushProcessWriteBuffers
  (an IPI-backed kernel call); QueueUserAPC and alertable waits; vectored
  exception handlers ahead of SEH; large cheap reservations.
- **M0d Universal CRT.** An original `ucrtbase.dll` with the
  `api-ms-win-crt-*` API sets forwarding to it, written as Doors' other
  DLLs (both widths): the functions the target runtimes import, measured
  from their import tables (stdio, string, conversion, heap, locale, math,
  time, environment, filesystem, process, runtime startup), with Windows'
  semantics checked against the reference PC. msvcrt.dll stays.
- **M0e Globalization.** kernel32's NLS functions on the Unicode
  collation and locale data (an upstream Rust implementation, ICU4X, if the
  owner approves the dependency), time-zone data as an updatable resource.
- **M0f Schannel.** secur32's SSPI with the Schannel package over Doors'
  TLS client (and a server side for SslStream.AuthenticateAsServer), with
  crypt32's chain engine for certificate policy.
- **M0g Activation contexts.** Application and DLL manifests,
  CreateActCtx/ActivateActCtx, comctl32 v6 selection.
- **M0h Capacity.** The owner's capacity pass: processes, ports, private
  DLLs per process, and executable images mapped from the file rather
  than captured whole (so the 1 MiB limit goes; the image hash for User
  Account Control is computed while reading). Needs the owner.
  Processes done ahead of the P17 gate (owner, 13 November 2026): 32 slots,
  the kernel arenas re-laid out for them (see RISKS); threads, ports,
  private DLLs and the image size remain for this milestone.
- **M0i CNG.** bcrypt.dll (hashes, HMAC, AES modes, RSA and ECDSA,
  ECDH, BCryptGenRandom from kernel entropy) and ncrypt.dll (persisted
  keys in the user's and machine's key stores, over the existing
  CryptoAPI containers), with one semantic owner shared with advapi32's
  CryptoAPI (section 108). Windows reference probes as for CRYPT-A.
- **M0j C++ runtime contract.** Full C++ exception dispatch on both
  widths (`__CxxFrameHandler3/4` behaviour exercised through the shipped
  vcruntime140.dll, RtlUnwindEx with target frames, collided unwinds,
  rethrow, nested exceptions), and app-local vcruntime140/msvcp140 loading
  as private DLLs; fixtures built with the pinned MSVC `/EHsc` and `/MD`.
- **M0k Inter-process plumbing.** Named pipes (server and client, message
  mode, overlapped, impersonation level), file mappings shared by name,
  and job objects with kill-on-close, at the counts the runtimes need.
- **M0l Diagnostics.** dbghelp's stack walking and symbol loading from
  PDBs beside the binary (managed and native crash reports), and the
  minidump writer used by runtimes' crash handlers.

### M1 — modern .NET (RUNTIME-A, console and services)

The current .NET LTS runtime, unmodified (MIT), x64 then x86: `dotnet`
host resolution, a self-contained and a framework-dependent application.
Fixtures: allocation churn across GC generations, threads and
synchronization, exceptions through managed and native frames, P/Invoke
and COM interop, file and network I/O (HttpClient over Schannel to the
test endpoints), globalization (cultures, sorting, time zones), a hosted
runtime (hostfxr from a native process), a .NET Windows service. Named
workflow: a real open-source .NET console tool run on real data
(chosen with the owner), installed through its MSI or zip.

### M2 — Windows Forms (RUNTIME-A)

An original `gdiplus.dll` (the flat API Windows Forms and System.Drawing
use: graphics, paths, brushes, pens, fonts and text, images with
PNG/JPEG/GIF/BMP/ICO codecs, metafiles as needed), then the .NET Desktop
Runtime's Windows Forms. Named workflow: a multi-window Forms application
with dialogs, data entry, clipboard, DPI change and saved state across a
restart.

### M3 — legacy .NET Framework (owner decision)

.NET Framework 4.8.x is proprietary and installs as a Windows component;
running it needs the owner's decision on its redistribution terms and on
mscoree's role. If approved: mscoree.dll's shim, the Framework's
installation, a Forms workflow on the Framework.

### M4 — other runtimes (RUNTIME-A)

Unmodified Windows builds, each its own record: Python (the embeddable
distribution and pip wheels with native extensions), OpenJDK (HotSpot's
JIT, safepoints and signals over SEH), Node.js (V8, libuv over IOCP and
named pipes). Named workflow per runtime.

### M5 — WinRT and packages (RUNTIME-A)

combase's Windows Runtime: HSTRING, IInspectable, activation factories,
RoInitialize apartments, metadata (.winmd) resolution, async operations,
delegates and events, error propagation; a C++/WinRT console fixture.
Then package identity and deployment (MSIX: AppxManifest, dependency
resolution, registration, activation, removal). WinUI 3 and the Windows
App SDK depend on DirectX composition (P19/P20) and are scheduled there.

### M6 — WPF (RUNTIME-A, after the text prerequisite)

WPF's software rendering path (no Direct3D), which needs a DirectWrite
subset (font collections, text layout and shaping, glyph runs) shared
with P20 and the browser track. Named workflow: a WPF application with
binding, layout, text input, resize and saved state.

### M7 — browsers and embedded browsers (BROWSER-A)

Prerequisites: job objects, restricted tokens and integrity levels for
the sandbox, named pipes and shared memory at Chromium's scale, the
DirectWrite subset, software GPU (SwiftShader-class) rendering, M0h's
capacity. Target: an Electron sample application and the WebView2
runtime's evergreen distribution (owner decision on its terms), then a
browser. Named workflow: navigation, downloads, permission prompts and a
renderer crash recovered.

## Records each runtime keeps

Section 110 asks for an adoption record per runtime: its exact version and
binary identity, path (unmodified Windows distribution or native port),
license and redistribution terms, CPU requirements, JIT executable-memory
policy, unwind and exception dependencies, diagnostic interfaces, the
imports and runtime calls measured, and who updates it. Each milestone
also publishes why its named application was chosen and its version.
Application models keep separate profiles (classic Win32, packaged
desktop, UWP-style, Windows App SDK), and unavailable cloud services,
Store authorization or attestation are recorded as such, never spoofed.

## Progress (14 November 2026, p18 working copy; host-tested and linted, not yet run in a guest)

- **M0b wired:** Windows VirtualAlloc/Free/Protect now run over per-page
  reservations from the page pool (`kernel/src/process/vm/windows_memory.rs`):
  any free 64 KiB-aligned range outside the native fixed layout, top-down
  reservations, every private protection with W^X toggling and guard pages
  (user page faults reach `Vm::windows_fault`), commit charge against the
  pool, release at process teardown. New ops VM_QUERY (VirtualQuery(Ex),
  MEMORY_BASIC_INFORMATION in both widths) and VM_FLUSH_WRITE_BUFFERS;
  kernel writes into user memory go through `Vm::validate_write`, which
  flips EXECUTE_READWRITE pages writable first. Kernel mapping and
  allocation records 640 -> 1,024 (frame records moved out of line).
- **M0c started:** futex-style WAIT_ADDRESS/WAKE_ADDRESS in the scheduler
  (bucket sequences, no user memory read under the lock); ntdll SRW locks,
  critical sections, condition variables, WaitOnAddress, SLists, FLS;
  semaphores (HandleKind 18; scheduler wait objects 32 -> 256); PRECISE_TIME
  (invariant TSC calibrated on the PM timer) for QueryPerformanceCounter;
  MEMORY_STATUS for GlobalMemoryStatusEx; processor/cache/NUMA/affinity
  queries, version checks, error modes, pointer encoding; locale basics for
  en-US and invariant (M0e still owns real globalization); GetFullPathName;
  GetModuleHandleEx; FormatMessage; console and named-object stubs.
- **x64 SEH:** a complete RtlVirtualUnwind (`compat/pe/src/x64_unwind.rs`,
  host tests: prologs, epilogues, tail calls, chained info, machine frames,
  handlers, context pointers) and an ntdll dispatcher (`seh64.rs`):
  frame-based dispatch after vectored handlers, RtlUnwindEx with unwind
  consolidation for C++ catch funclets, RtlCaptureContext/RtlRestoreContext,
  RtlRaiseException/RaiseException, dynamic function tables (plain,
  callback, growable), the unhandled-exception filter, Get/SetThreadContext
  of suspended threads (THREAD_GET/SET_CONTEXT). Faults enter through an
  assembly stub with a machine frame, as through KiUserExceptionDispatcher;
  delivered CONTEXTs now carry FXSAVE state, and a new fault replaces a
  stale pending continuation.
- **Images in page-pool memory:** kernel-planned modules (the start-up
  bundle, provider loads, private loads) are now MEM_IMAGE reservations of
  pool pages (`Vm::map_images`), filled and fixed up through the pool's
  aliases, then protected per section; no alias window or contiguous
  frames. Rollback checks compare frames outside the pool and pool pages.
- **Decision (14 November 2026): application DLLs load in user mode.** The
  kernel-planned path keeps fixed limits at every step (1 MiB capture
  slots, 4 private DLLs per process in 32 MiB slots, 16 modules per plan).
  As on Windows, ntdll's loader will map application DLLs itself over the
  shared `door_pe_loader` parser: reserve the image (MEM_IMAGE), commit and
  read the sections from the file, relocate, resolve imports against both
  kernel-mapped and user-loaded modules (export lookup, forwarders, API
  sets), set section protections, run TLS callbacks and DllMain with
  reference counts, and publish the module to GetModuleHandle,
  GetProcAddress and the unwinder. The main executable follows (a process
  starts on ntdll, which maps the program from its file), which also lifts
  the 1 MiB executable limit (VS Code's executable is about 150 MB).
- **Still missing for .NET's start-up imports:** file mapping
  (CreateFileMapping/MapViewOfFile(Ex)/UnmapViewOfFile), thread-pool
  timers, named-pipe server calls, GetFinalPathNameByHandleW, the UCRT
  (M0d), image size (coreclr.dll is 4.6 MB; images are captured whole up to
  1 MiB), threads (`MAX_TASKS` 16) and one scheduler CPU (M0h).

## Order and parallelism

M0a, M0b and M0d first (every track needs them), with M0c beside M0b and
M0j after M0d; M1 starts as soon as they land. M0e, M0f, M0g, M0i and M2
follow M1's console results; M0k and M0l before M4 and M7. M4 shares M0's work and can run beside M2. M5 is independent of
M2 to M4. M6 and M7 wait for the DirectWrite subset and the capacity
pass. Each milestone's first step is an import and runtime-call inventory
of its target binaries (section 108), so the work list is measured, not
guessed.

## Bare metal from the start (owner, 13 November 2026)

Later phases boot on physical PCs, so nothing in P18 may be shaped by
QEMU: memory is demand-paged one page at a time (no physically contiguous
user regions, no standing kernel aliases of user memory); limits come from
the RAM and processors found at boot, not constants tuned for a 2 GiB
guest; device drivers time out with clocks that run with interrupts off
