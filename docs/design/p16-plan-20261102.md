# P16 shells, elevation and installers — plan and progress

P16 in the master specification is "COM, services, and installers" (gates
PLATFORM-A and INSTALL-A). The owner added the command-line and elevation
work below to it on 2 November 2026: a complete cmd.exe, Doorsh (the native
shell), Terminal profiles, legacy entry points redirected to the modern UI,
User Account Control with Run as administrator, and Authenticode signature
checking. The phase ledger still records P16 as not started; nothing here
qualifies the phase gate.

## Done (2 November 2026)

- **cmd.exe** (`crates/shells/src/cmd`): resumable engine with batch files,
  `SET /A`, `FOR /L /F`, redirection, `IF`, `CALL`, `%~` modifiers, errorlevels
  (9009 for unknown commands), the Windows banner and `ver` as Macrohard Doors,
  `ipconfig`, `whoami /groups` and administrator tools that follow the token
  (elevated or filtered).
- **Doorsh** (`crates/shells/src/doorsh`): the native shell with structured
  values and pipelines (`where`, `sort`, `select`, `count`), expressions,
  `.dsh` scripts with functions, `try`, loops, aliases and help; unknown
  commands fall through to cmd.exe; deleting several items or a folder tree
  asks first and protected locations are refused.
- **Terminal**: Doorsh, Command Prompt, PowerShell and DSL profiles with their
  icons and tab titles, a collapsible profile rail, F11 full screen (the
  window server hides the taskbar), the Home page (recent folders, scripts),
  `.bat`/`.cmd` opening in Terminal.
- **Legacy entry points**: Run and Start search resolve legacy programs
  (`regedit`, `control printers`, `wordpad`, ...) to their Settings pages or
  apps (`frameworks/settings-map`); `doorsh`, `cmd`, `powershell` and `dsl`
  open Terminal on that profile.
- **User Account Control** (`graphics/window-server/src/uac.rs`): the window
  server draws the consent prompt over a dimmed secure desktop that owns all
  input; No is the default, Alt+Y approves. Administrator pages of Settings,
  "Run as administrator" in Start and Terminal administrator tabs use it.
- **Authenticode** (`crates/authenticode`): the image digest, PKCS #7 signer,
  code-signing chain, RFC 3161 and countersignature timestamps and the
  hardened padding check, per Microsoft's PE signature format; the publisher is
  the signer's simple display name. Trust anchors: the Mozilla roots plus
  Microsoft's and the public CAs' code-signing roots (`roots/README.md`).
  Fixed-date fixtures cover valid, tampered, untrusted, expired, timestamped,
  late-timestamped and untrusted-timestamp cases. On this PC it agrees with
  Windows for git-bash.exe (Johannes Schindelin), node.exe (OpenJS Foundation,
  valid only through its timestamp), link.exe and wsl.exe (Microsoft
  Corporation); catalog-signed System32 files report Unsigned (catalogs are not
  read).
- **Run as administrator in File Explorer** (`window::REQUEST_ELEVATION`):
  File Explorer hands the path and the program's bytes to the window server.
  The server verifies the signature itself, names the program by its version
  resource's FileDescription, and shows the verified publisher or the
  unknown-publisher prompt. On approval it asks Init to start the program
  (`application::EXECUTE_ELEVATED`, window server only). Init starts it only if
  the bytes it loads hash to the approved SHA-256. A batch file opens an
  administrator Terminal tab instead.

- **Secure desktop**: while the prompt is open the backdrop is the screen
  frozen as it opened (nothing an app draws afterwards shows), IME candidate
  windows stay off it, and the On-Screen Keyboard's synthesized keys are
  refused, so no app or tool can answer the prompt.
- **File Explorer types** (2 November): stock Windows 11 26H2 file-type icons
  for programs, batch files, installers, system files, settings, PowerShell,
  registry, shortcuts, fonts, disc and disk images, cabinets, certificates,
  archives, images (Photos) and media (Media Player), taken from each type's
  default association on the reference PC (`assets/icons/windows/file-*.source.json`);
  the Type column uses the associations' friendly names (Doors for Windows;
  "EXT File" otherwise). Programs show a Digital signature section in Details
  and a summary (publisher, signature, version) in Preview; the details' PE
  subsystem reads "Interface: Desktop app / Command line". The native root is
  "Doors" in the address bar, and "Your tags" (with Create tag) and "Add
  tag" in the context menu are always available.

Guest evidence: `cargo xtask test p16-cmd --image <image>` (cmd.exe commands,
F11, the regedit consent prompt, Doorsh, Run as administrator on an unsigned
program and on a batch file); `cargo xtask test terminal`.

## Not done

- **Token model.** Elevation is real for the shells (cmd/Doorsh administrator
  tools follow the token) but Windows programs have no token yet: an approved
  program runs as the session user like any Explorer launch.
- **Users, groups and privileges**: standard users, the credential variant of
  the consent prompt, and the multi-user sign-in page.
- **Open File – Security Warning** (mark of the web) before downloaded
  programs and installers; installer detection (requireAdministrator
  manifests, setup heuristics) raising the prompt on Open.
- **Installers**: MSI, the Windows C: folder layout installers expect, file
  associations and deployment journaling (INSTALL-A).
- **COM, RPC, the service control manager and task/event foundations**
  (PLATFORM-A); advapi32 and the other missing Win32 APIs.
- **Catalog signatures** (`.cat` files) and revocation checking (done 9
  November 2026: wintrust.dll, see "M5 paths to MAX_PATH, catalogs,

- P16 gate wiring in xtask, ledger records and a critic review.

### Not done yet (recorded, not hidden)
- Loading a system DLL that a program does not import (LoadLibrary of

  program's import closure. COM-A links dsound.dll until it does.
- Registry values hold 64 bytes, so InprocServer32 is the expanded path
  (REG_SZ) instead of Windows' `%SystemRoot%\System32\dsound.dll`

  environment blocks and handle inheritance are not carried.
- ShellExecute of a file with no registered program: Windows 11 opens the
  "How do you want to open this file?" picker; Doors answers

  Windows programs (Shell_NotifyIcon fails with ERROR_NOT_SUPPORTED),
  SHBrowseForFolder; FOF_ALLOWUNDO deletes are refused (no Recycle Bin
  for Windows programs) rather than made permanent.
- Out-of-process COM (LocalServer32 answers CO_E_SERVER_EXEC_FAILURE),
  marshaling, oleaut32, rpcrt4 (M6).
- **Windows paths in storage**: ntdll now hands storage two path forms:
  drive- or backslash-rooted paths as Windows paths on C: (`C:\a\b`, which
  storage-core resolves case-insensitively through the `/compat` view and
  its `C:\Users` -> `/users` mapping) and slash-rooted paths as native ones
  (`/system/bin/app.exe`, the form Doors gives a program for its own
  folders). Every storage file operation (METADATA, LIST, MKDIR, REMOVE,
  RENAME, OPEN, METADATA_FOR, OPEN_FOR) accepts both; Init's EXECUTE and
  the User Account Control glue accept `C:\` paths. Before this, Windows
  programs' directory calls only worked with the exact native case
  (`C:\users\1001`).
- **C: layout, first part**: a new volume gets `C:\Program Files`,
  `C:\Program Files (x86)` and `C:\ProgramData` (system-owned, readable by
  everyone, beside the existing `C:\Windows\System32`). Existing volumes do
  not get them yet.
- **Run as administrator from File Explorer** (p16-cmd's last step) is
  refused: Init verifies the image and then `process_execute` answers
  Denied (`DOOR_P16 EXECUTE failed code=Denied elevated=true`, now logged).
  The elevated launch path came from the earlier session untested; it is
  M5 work.

## Progress (4 November 2026): runtime DLL loads, cabinets, Windows Installer

- **A second LoadLibrary of a system DLL** (COM-A's winmm.dll after COM
  loaded dsound.dll) failed: every runtime load started its kernel alias
  window at the same offset and the first load's regions keep theirs.
  `module_alias` now places a load after every alias already in the
  window, bounded by the process's arena. ntdll maps the kernel's answers
  to Windows' codes (ERROR_INVALID_ADDRESS, ERROR_BAD_EXE_FORMAT, ...) and
  the kernel logs `DOOR_P16 PROVIDER_LOAD` on a refused load. COM-A 9/9 in
  the guest (`host-1793768497383001000-3444`).
- **Windows applications' commit limit** is 192 MiB of the 256 MiB dynamic
  window (was 64 MiB), console programs included. A failed heap
  allocation now logs `DOOR_HEAP exhausted request= mapped= segments=`
  once per process, and a panicking GUI DLL prints its message (an
  allocation's size) beside the location.
- **`crates/cab`** (door-cab): MS-CAB cabinets — stored, MSZIP (deflate
  blocks sharing a 32 KiB window) and LZX (15..21-bit windows, verbatim,
  aligned and uncompressed blocks, matches across frame ends, E8 call
  translation), CFDATA checksums, a writer (stored and fixed-Huffman
  MSZIP). Checked against makecab.exe's LZX:21, LZX:15 and MSZIP output;
  Windows' expand.exe extracts the writer's cabinets byte for byte.
- **`crates/msi`** (door-msi): Windows Installer databases — the compound
  file (v3/v4, DIFAT, mini stream), encoded stream names, the string pool
  (long references, code pages), the `_Tables`/`_Columns` catalog and
  column-major tables, OBJECT columns' streams, summary information.
  `install::plan` resolves properties (the package's, Doors' folders as
  Windows Installer reports them, the command line's), features at
  INSTALLLEVEL and the Condition table, component conditions (the full
  condition grammar), the Directory tree (DefaultDir target names,
  directory properties), files with their cabinet (`#embedded` or beside
  the package, per-file compression bits), CreateFolder, Registry values
  (`#`, `#x`, `#%`, `[~]`, formatted `[Property]`, `[#file]`,
  `[$component]`), shortcuts (advertised ones to the component's key
  path) and the Add/Remove Programs entry. `execute` carries a plan out
  over a file-system and registry `Target` and caches the package under
  `C:\Windows\Installer` with the Installer's InstallProperties (packed
  product code); removal works from the cached package. `link` writes .lnk
  files (header, item ID list, LinkInfo, strings) that Windows' own shell
  reads back (target, arguments, description, working directory, show
  command). Tested on a package built by Windows Installer's database
  engine on the reference PC.
- **msiexec** in cmd: `/i`, `/x` (package or product code), `/qn` and the
  other UI levels, `/l*v`, `PROPERTY=value`; Windows Installer's exit
  codes (1925 for a per-machine package on a standard token, 1605, 1619,
  1620, 1639).
- **Process regions**: a process may hold 160 VM regions (was 64; a GUI
  Windows program maps every section of a dozen DLLs plus stacks, heap
  segments and window sections — SHBrowseForFolder ran out). The region
  records moved out of `ProcessSpace`, which travels by value through
  kernel stacks, into per-slot tables in the static VM owner. SHELL-A's
  main probe passes 11/11 in the guest (`host-1793773217849792200-19260`);
  its separate notification-area run (`shellprobe tray`) still fails at
  Shell_NotifyIcon NIM_ADD.
- **INSTALL-A** (`cargo xtask test p16-install`, not passing yet): the
  sample package reaches the guest through the image's system share and
  File Explorer's copy; a standard token gets 1925. The run as
  administrator fails because an administrator Terminal tab is a flag in
  the Terminal process, not an elevated token: its storage requests still
  carry the user's identity, so C:\Program Files and HKLM refuse the
  writes. Windows performs installations in its Installer service as
  SYSTEM; the Doors equivalent needs M5 first — elevated processes for
  approved programs (a native `msiexec` launched through Init's
  EXECUTE_ELEVATED), Administrators' modify access on the C: system
  folders and HKLM. Init itself stays allocation-free and does not parse
  packages.

What it took beyond `crates/msi`, `compat/dlls/msi` and msiexec.exe:

- **Private DLLs (kernel, ADR 0022).** `WINDOWS_PRIVATE_LOAD`: LoadLibrary
  of a DLL that is not a system DLL hands its bytes to the kernel, which
  captures them, plans the DLL with the process's modules at one of four
  private slots after the system DLLs (relocated there, with the system
  DLLs its imports need) and maps it; ntdll runs DLL_PROCESS_ATTACH. A
  second load of the same bytes answers the mapped one. Dynamic memory is
  still never executable.
- **Paths.** CreateProcess's working folder and `DoorGetNativePath` give
  the stored native spelling of a `C:` path (components matched without
  regard to ASCII case); cmd's PATH search does the same
  (`C:\Windows\system32`); an elevated program's argv[0] is its Windows
  path (`GetModuleFileName`), as Explorer starts it.
- **msiexec's own quoting** (`split_msiexec_line`): a backslash before the
  closing quote stays a backslash, `""` is a quote; the hand-off to the
  elevated copy writes values the same way.
- **WriteRegistryValues formats values when it runs**, so a custom
  action's property set after costing reaches the registry.
- **File Explorer's address bar** opens a typed file as a double-click
  does (a package goes to Windows Installer).
- **Fidelity.** User Account Control names the .msi, not msiexec.exe
  (`elevation::PACKAGE`); a multiline edit without ES_AUTOHSCROLL wraps
  (the license text); the caption shows the buttons WS_MINIMIZEBOX /
  WS_MAXIMIZEBOX ask for (a dialog frame: Close only; one of the two: the
  other greyed and inert).
- **Gate.** `verify --phase P16` adds clippy of msi.dll and advapi32 on the
  PE target and the host suites of door-cab, door-msi, door-msi-dll and
  door-shells.

Deviations (recorded, not hidden):

- The rollback journal lives in `C:\Windows\Installer\Config.Msi`: the
  Doors drive's root is not writable even for Administrators.
- DLL custom actions run in the installing process (msiexec.exe or the
  caller of MsiInstallProduct), not in a separate custom-action server.
- Script custom actions (VBScript/JScript) fail with 2738/2739: Doors has
  no script engines.
- A SharedDLLs value whose path exceeds the Doors registry's 48-unit value
  names is named `#` and the FNV-1a hash of the lower-case path.
- The handoff to the elevated copy goes through
  `HKCU\Software\Microsoft\Installer\Handoff`; the non-elevated copy exits
  0 once User Account Control opens.
- Settings' Uninstall confirmation is drawn as a menu, not Windows'
  flyout.
- Doors runs at most 13 processes and the session holds nine: INSTALL-A
  closes Terminal before the elevated batch so msiexec and the programs
  its custom actions start fit, and p16-cmd closes Settings before its
  elevated batch (the kernel's address layout fixes the limit; the owner
  deferred a capacity pass until after M1–M9).

Regressions on the same image (8 November 2026): p16-cmd, p16-com,
p16-shell, p16-accounts and p16-scm pass. p15-connect's IOCP-A failed at
"receive-event" (an event-signalled WSARecv got neither its event nor its
port packet): kernel handles were a global counter, so an event handle
could be odd and DoorCompleteIo read its low bit as Windows' "no port"
flag. Kernel handle values now start at 0x10000 and step by 4
(`HANDLE_FIRST`, `HANDLE_STRIDE`), as Windows' handles are multiples of
four and clear of the console (0x100..) and registry key (0x4000..)
handles. iocpprobe reports which part of step 4 failed. On the image with
that change (`host-1794111471299884600-25100`) all seven pass:
p15-connect (IOCP-A 9/9, `host-1794112203459153600-11624`), p16-install
(`host-1794112435917068300-24572`), p16-cmd, p16-com, p16-shell,
p16-accounts and p16-scm.

## Progress (8 November 2026): M7 service recovery, hung controls, denial, Services page

- **Failure actions** (SERVICE_CONFIG_FAILURE_ACTIONS and
  _FAILURE_ACTIONS_FLAG through Change/QueryServiceConfig2): stored where
  Windows keeps them (FailureActions REG_BINARY with its 20-byte header,
  RebootMessage, FailureCommand, FailureActionsOnNonCrashFailures). Init's
  manager counts a service's failures (a process that ends without
  STOPPED, or STOPPED with an error when non-crash failures count), starts
  the count over after the reset period, logs event 7031 (with the
  corrective action) or 7034 (none) to the System log, and restarts the
  service after the action's delay as the user who started it. Restart
  needs SERVICE_START on the handle, as on Windows. Restarting the
  computer is refused with ERROR_ACCESS_DENIED (Doors' tokens hold no
  shutdown privilege) and running a program with ERROR_NOT_SUPPORTED;
  four actions at most.
- **Controls wait for the handler**: each control gets a sequence number;
  the service's dispatcher reports when its handler returned, and
  ControlService waits for that. A handler that does not return (or a
  control nobody takes) in 30 seconds fails the call with
  ERROR_SERVICE_REQUEST_TIMEOUT and logs event 7011
  (`scm::CONTROL_DONE`, `CONTROL_STATE`).
- **Settings > Services** (services.msc behind User Account Control, as
  the Management Console asks) lists what the manager knows, with a serial
  line for tests.
- **Fixed**: Terminal's `sc delete` and `reg delete <key>` opened the key
  without DELETE access, so storage refused them.
- **Fixtures**: doorsvc.exe crashes (Mode 1) or hangs in its stop handler
  for 40 seconds (Mode 2) and counts its starts; svcprobe.exe adds the
  recovery, crash-loop and hung-stop steps and a `denied` mode for a
  standard user (SCM-D).
- **Guest evidence**: `cargo xtask test p16-scm` passed on image
  `host-1794134661694164400-10460` (run `host-1794135331245561400-24460`):
  SCM-D 3/3 (all-access manager refused, listing allowed, SERVICE_STOP
  refused); SCM-A 12/12 (the crash loop ran the service three times and
  left it stopped with exit code 3; the hung stop failed after 30 s with
  1053, stayed STOP_PENDING and then stopped); the System log's 7036,
  7031 (twice), 7034 and 7011 events; eventcreate/wevtutil; schtasks; the
  Services page listing an `sc`-created service as stopped beside Doors'
  running services.
- **Still open in M7**: the Task Scheduler's COM API (ITaskService and
  its IDispatch interfaces need oleaut32, so it follows M6, as WASAPI
  does); Event Log messages are cut at 168 bytes (one IPC payload), which
  shortens a 7031 message for a long service name; failure actions that
  run a program or restart the computer.

## Progress (9 November 2026): M5 tokens, security functions, accounts, Open with

- **Standard users' tokens.** The kernel's session records whether its
  account is an administrator (SESSION_CREATE's third argument, from the
  session service's account book); an administrator's applications carry
  `group::ADMINISTRATOR_ACCOUNT` (Administrators for deny only), a standard
  user's do not. advapi32's token is then Windows' in all three shapes:
  elevation type Default/Limited/Full, groups in Windows' order (the
  integrity label first, S-1-5-114 and Administrators only for an
  administrator, S-1-5-113 Local account), no linked token for a standard
  user (ERROR_NO_SUCH_LOGON_SESSION), the linked token an identification
  token of the other elevation (its buffer exactly 8 bytes, else
  ERROR_BAD_LENGTH), TokenDefaultDacl, TokenLogonSid, TokenImpersonationLevel,
  impersonation (ImpersonateSelf, RevertToSelf, SetThreadToken,
  ImpersonateLoggedOnUser, DuplicateToken(Ex) making impersonation tokens),
  CheckTokenMembership needing an impersonation token (1309), and
  AdjustTokenPrivileges keeping each token object's privilege state with
  PreviousState. `whoami /groups` leaves out Administrators for a standard
  user. Local SIDs have Windows' three machine sub-authorities
  (S-1-5-21-2026-26300-1-RID).
- **Security descriptors and SDDL** (`compat/dlls/advapi32/src/security.rs`):
  absolute and self-relative descriptors and ACLs in caller memory
  (Initialize*, Get/Set*, MakeSelfRelativeSD, MakeAbsoluteSD, AddAce,
  Add*AccessAce(Ex), AddMandatoryAce, GetAce, DeleteAce, GetAclInformation),

  elevated COM lookups read HKLM only; Init's COM relay is scoped by
  session, user and elevation, with per-connection quotas and random OIDs;
  deny entries for Administrators apply to unelevated administrators.
- **Services** (owner decision of 11 November 2026, ADR 0026 item 6): a
  service account, LocalSystem (uid 18, S-1-5-18), whose logon permit only
  Init holds; its session opens at the first sign-in of the boot and
  outlives sign-out; services and their programs run there with the full
  token (GetUserName SYSTEM, the systemprofile profile, USERNAME
  `COMPUTER$`). The SCM starts dependencies first (1075, 1068, 1059 on a
  cycle; `sc qc` prints DEPENDENCIES), passes ImagePath's arguments, and
  hands StartService's arguments (`sc start <name> <words>` too; 128 bytes
  at most) to ServiceMain after the service's name. SCM-A's service
  records its account, LocalSystem SID, elevation and start arguments,
  and the scenario checks them.
- **Run as administrator**: ShellExecuteEx "runas" waits for the user's
  answer (ERROR_CANCELLED, or the process handle with
  SEE_MASK_NOCLOSEPROCESS) and passes lpParameters as CommandLineToArgvW
  splits them, empty arguments included; a request that Init's launch
  message cannot hold is refused before the prompt; the display service
  keeps up to eight requesters' outcomes and drops a requester's when it
  disconnects; shell32 checks the program's size before reading it.
  lpDirectory is not honoured (ADR 0024).
- **Windows Installer**: RegisterClassInfo, RegisterProgIdInfo, the MIME,
  Font, TypeLib, SelfReg, Environment, IniFile, DuplicateFile, MoveFile,
  IsolatedComponent and PublishComponent tables are carried out and
  reversed (`crates/msi/src/install/tables.rs`, `engine/tables.rs`), each
  registry row by the action that owns it; registry writes go to the view
  of their component's bitness and a package of the other bitness runs in
  that msiexec.exe (`/y`, `/z` and type-library registration cross over
  too). Patch, ODBC, MsiAssembly, Complus, SFPCatalog, MsiServiceConfig
  and administrative installation fail with 1603; LockPermissions and a
  non-LocalSystem StartName are logged (ADR 0022). INSTALL-A gained a
  32-bit package with classes, a type library, a font, environment and INI
  changes, verified and removed.
- **Parsers**: the Authenticode certificate-table offset, the type-library
  parameter offset and the compound file's directory chain are bounded.
- **Gate**: ordered `require` steps in INSTALL-A; SCM-A's dependency,
  account and argument checks. Negative elevation-boundary cases beyond
  SCM-D's standard user are host-tested for Init's admission (the user's
  and the service session's boundaries, `init::admission_tests`); guest
  cases for the hand-off key and the COM relay are still to be added
  (NEXT_STEPS).
- **Remaining deviations**: services share the signed-in user's desktop
  (no session 0; ADR 0026), the 16-service limit, no rpcrt4/NDR (COM over
  Init's relay), four ACL entries per file, registry keys without
  descriptors.
